## 起因：一篇别人的 CLI 文章

前两天刷到 Zero 的《给博客写个本地管理 CLI》（[vtdd.vip](https://vtdd.vip/posts/%E7%BB%99%E5%8D%9A%E5%AE%A2%E5%86%99%E4%B8%AA%E6%9C%AC%E5%9C%B0%E7%AE%A1%E7%90%86-cli/)），他给自部署的 Firefly 博客写了约 400 行纯标准库 Python：本地建文、写动态、管友链，然后 SMB 推服务器、SSH 触发 Docker 重建。

看完的第一反应是：他的「同步/重建」那套我完全用不上——本站部署在 Cloudflare Pages，push 即上线，git 本身就是最强的同步工具。但「**把内容操作命令化**」这个思想是通的：建文章不该是"复制模板、手改 frontmatter、祈祷没漏逗号"，管友链不该是"打开 TS 文件、肉眼找数组、手敲对象"。

对照本站现状，真正值得抄的就三样：

1. **内容操作命令化**：建文、加友链、发布，都收敛成一条命令或一个按钮；
2. **友链数组定位技术**：用括号深度配对在源码里精确定位数组边界，只动数组体、绝不碰其他代码；
3. **工程习惯**：所有写操作支持 `--dry-run` 演练，发布前显式确认。

另外他有一条例子值得记死：`.bak/.tmp/.old` 备份文件放进 `src/` 会被 Astro 当源码编译，直接炸构建。这条我顺手写进了本站的维护备忘。

## 第一阶段：CLI 原型

先花半小时做了个零依赖的 Node 原型 `scripts/blog.mjs`（约 250 行），验证算法可行性：

- `post "标题"`：生成规范 frontmatter（`published` 自动填当天、CRLF 行尾），slug 强校验 `^[a-z0-9]+(-[a-z0-9]+)*$`——中文标题必须显式给英文 slug，否则拒绝，从源头杜绝百分号编码的 URL；
- `friend-add "名字" -u URL`：括号深度配对定位 `friends` 数组，只在数组尾部插入对象块，重名/重 URL 直接拒绝；
- `publish`：列出 git 变更 → 交互输入 `yes` 确认 → add + commit + push。

核心算法其实是那个「括号深度定位」：从数组声明行开始逐字符扫描，遇 `[` 深度 +1、遇 `]` 深度 -1，深度归零的位置就是数组结尾，插入点定在最后一个 `}` 之后。这样做的好处是**正则只负责找起点，结构靠扫描确定**，不会被代码格式变化搞崩。

原型测试通过后问题来了：CLI 再顺手，也得切终端、敲命令。我日常写文章用的编辑器是自托管的 Wails 应用「轻阅」（Go + 原生 JS 的桌面 Markdown 编辑器）——**为什么不让编辑器自己长出这个后台？**

## 第二阶段：集成进轻阅

Wails v2 的绑定机制对这种集成非常友好：Go 端 `App` 结构体上的公开方法，构建时自动生成前端可调用的绑定。所以整件事的架构就是：

```
前端面板（JS） ──桥接──> Go 方法（blog.go） ──> 直接读写博客仓库
```

Go 端落了 8 个方法：

| 方法 | 职责 |
| --- | --- |
| `GetBlogSettings` / `SetBlogSettings` | 仓库路径、git 路径的持久化配置 |
| `ListBlogPosts` | 解析每篇的 frontmatter，按日期排序 |
| `CreateBlogPost` | 建文（slug 校验、重名拒绝、原子写入） |
| `ListBlogFriends` / `AddBlogFriend` | 友链的读取与插入（括号深度定位） |
| `PreviewBlogPublish` | git status 预览变更 + 默认提交说明 |
| `PublishBlog` | add → commit → push，带超时保护 |

几个设计决定值得展开：

**配置校验前置**。保存仓库路径时立刻检查目标目录含 `.git` 和 `src/content/posts`，把"路径填错"拦在配置阶段，而不是等到列表拉空了再排查。

**发布必须显式确认**。点发布先弹确认框，且发布前能用「检查变更」看到将要提交的文件列表——因为 push 就是"下令上线"，静默 push 等于替用户做决定。这也是从 CLI 的 `yes` 确认机制原样继承来的。

**文章列表点击即编辑**。列表返回每篇的绝对路径，点击直接在编辑器里打开该 md，写完回面板点发布——整个闭环不离开轻阅。

## 踩坑记录（这部分最值钱）

制作过程不长，坑倒是一个没少吃：

**其一，编辑工具的"假成功"。** 批量修改文件时，工具报告成功但部分修改根本没写入磁盘。最离谱的一次，五处修改只落盘三处，编译报错才发现字段没加上；还有一次替换脚本把 `\n` 字面量吃成了真换行，直接把 Go 源码写坏。之后养成铁律：**改完代码必须回读确认关键行真的落盘**，批量修改后逐处 grep。

**其二，slug 被当路径用。** 面板第一版里，文章按钮存的是 slug（如 `encrypt-your-posts`），点击时却把它当完整路径传给了"打开文档"接口。Go 端拿一个相对路径去读文件，自然报"文件已删除或移动"——我盯着这个报错还先去查了权限问题，方向完全错了。修法是列表接口直接返回绝对路径 + 前端加兜底拼接。**教训：报"文件不存在"时，99% 是传进去的路径本身不对，别往权限方向查。**

**其三，Go 正则的行尾匹配。** 解析 frontmatter 的 `description:` 和 `category:` 都是多行文本里的单行匹配，`$` 在默认模式下匹配整个字符串末尾而不是行尾，必须加 `(?m)` 标志。这类错误不报错、只是静默解析为空，测试没覆盖到就一直潜伏。

**其四，安装包打包卡在 NSIS 缺失。** `wails build -nsis` 找不到 `makensis` 直接失败。不过主程序 exe 本身是自包含的（前端已内嵌），单文件就能分发，安装包属于锦上添花。

## 部署链路：编辑器和 CF Pages 之间没有魔法

集成完成后，整条链路是这样的：

```
轻阅写文章（直接写进博客仓库源码）
    ↓ 点「发布」
git add → commit → push 到 GitHub main
    ↓ push 触发
CF Pages 自动拉源码 → 云端 pnpm build
    ↓ 约 80 秒
blog.142588.xyz 生效
```

关键理解：**编辑器和 Cloudflare 之间没有任何直接通信**。CF Pages 当年绑定仓库时就配好了"监视 main 分支"，push 就是扳机，云端构建全自动。本地从头到尾不需要构建——本地 dist 只是预览用的临时产物。

于是写作流收敛成：**轻阅里写 → 点发布 → 确认 → 80 秒后上线**。以前"写完 md、切终端、敲 git 命令、等构建"的流程，现在只剩一个按钮。

## 尾巴

回头看，这次制作真正花时间的不是算法（括号定位、frontmatter 解析都是几十行的事），而是两件小事：一是决定"哪些环节值得自动化"——同步、构建这类 push 已经解决的问题坚决不碰；二是和"工具假成功"这类环境问题的搏斗。

工具链的意义就在于此：把重复劳动压到零，把注意力还给内容本身。这篇文章从轻阅面板里点开、检查、发布——它自己就是第一个用这套流程上线的作品。
